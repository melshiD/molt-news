Git for Book Writers: Why Version Control Matters When Writing with Claude

A plain-English guide for pastors and non-technical writers on using Git to protect and organize every version of a manuscript written with AI.

Published June 15, 2026
Author Kishbrac
Read time 13 min read
Audience Non-technical writers & clergy
The Problem

You've probably already lived this

You're working on your book with Claude. You ask it to revise Chapter 3. It gives you a new opening paragraph, but now you've lost the old one you liked better. You paste back and forth between browser tabs. You save a copy "just in case." Files named Chapter3_final, Chapter3_FINAL_v2, Chapter3_actually_final_this_time start piling up in your Documents folder. A week later, you can't remember which version had that illustration about the Good Samaritan. You open three files. None of them are right.

If this sounds familiar, you're not disorganized. The file-and-folder system that works well for finished documents was not built for the back-and-forth process of refining a manuscript through dozens of revisions over months.

There is a better way. It was built for software developers, but it works just as well for writers working with an AI collaborator. It's called Git.

What Is Git

A snapshot system for your manuscript

Git is a system that saves labeled snapshots of your writing. Every time you tell Git to save a version, it records exactly what your manuscript looked like at that moment, down to the word. You can return to any snapshot at any time, compare two snapshots side by side, and restore text from any point in your history. Those snapshots are permanent and searchable.

Here are the five concepts you need. Everything else is detail.

Repository called a "repo"
The folder that holds your entire book project, including its complete history. Think of it as an archive box containing not just your current manuscript but every draft you have ever saved, organized and searchable.
Commit saving a snapshot
Telling Git: "Save this version with this note." You might commit after finishing a writing session with a message like "Chapter 3, expanded the Good Samaritan illustration." That message becomes your breadcrumb. Months later, you can search your history for "Good Samaritan" and find exactly which version had it.
Branch an experiment lane
A separate copy of your manuscript where you can try something without changing your main draft. Create a branch called "chapter3-rewritten-opening" to experiment with a completely different approach. If it works, keep it. If not, delete the branch and your main draft is untouched.
Merge combining versions
Folding changes from one version back into another. You tried that experimental opening on a branch and it worked better. Merging it back into your main manuscript brings those changes in cleanly, alongside anything else you wrote while the experiment was running.
GitHub the online backup
A website that stores your Git repository securely online, accessible from any computer. If your laptop is lost or damaged, your entire manuscript history is safe. It also lets you share with a co-author or editor without emailing drafts back and forth.

The concepts will become natural as you use them. What matters now is the mental model: Git records every saved version of your writing, lets you name those versions, and lets you go back to any of them at any time.

Why Git & Claude Work Together

Four reasons this combination matters for writers

Git is useful for any writer working on a long project. It's especially valuable when you're working with Claude.

Challenge 1
Claude doesn't remember your manuscript
Each conversation with Claude starts completely fresh. Claude has no memory of what you worked on last Tuesday, what you agreed to change, or what Chapter 2 said three revisions ago. This is how AI assistants work. It means there's no built-in "go back to version 3" option when something goes wrong. Unless you saved it, it's gone. Git becomes Claude's external memory for your manuscript. Before you ask Claude to revise anything, commit the current version. That version now exists in your history forever, no matter what Claude does next.
Challenge 2
AI revisions are unpredictable
Sometimes Claude produces a revision that improves the structure. Sometimes it loses the pastoral warmth of your voice. Sometimes it changes the theological emphasis in ways that are subtle. You won't know which it is until you've read it carefully, and that can take days. Git lets you accept Claude's suggestions provisionally. The old version is saved. Read Claude's revision. Think about it. Show it to your elders. Then decide. There's no pressure to commit to the AI's version before you're ready.
Challenge 3
Writing with Claude is iterative
Writing a book with AI assistance involves many revision passes. You write a draft, Claude suggests revisions, you blend its ideas with your voice, Claude refines again, you edit for theological precision. After fifteen rounds, it's easy to lose track of what improved and what drifted. Git gives you a complete record: Draft → Claude revision 1 → your edits → Claude revision 2 → final polish. You can compare any two points in that history and see exactly what changed.
Challenge 4
Books take months
You might write Chapter 5 in January, then return to Chapter 2 in March. By March, you've forgotten what state Chapter 2 was in, what you were trying to fix, and what you'd already tried. Git's commit history is a precise log of decisions made over months: what changed, when, and what you wrote about why. Your commit messages become the record that lets you pick up exactly where you left off.
For pastors writing from a sermon series

When you're turning your sermon series into a book, Claude can help expand each sermon into a full chapter, adding context, deepening the exegesis, and smoothing transitions for a reader who wasn't in the room. Git lets you keep your original sermon text completely intact in its own file while Claude works on the expanded chapter version separately. At any point, you can compare the finished chapter back to the sermon you preached and ask: did we keep the core message?

A Realistic Example

Writing a book with Git and Claude: week by week

Let's walk through what this actually looks like. The book is Parables for Modern Life: A Pastor's Guide to Jesus's Stories Today. You're eight chapters in, working with Claude as your writing partner.

Each step below can be done two ways: using GitHub Desktop (a free visual application, no command line required) or by typing terminal commands. Both are shown.

Week 1: Setting Up

Creating your book's repository

You create a folder on your computer called parables-book. Inside it, you create files for your outline, your chapter notes, and Chapter 1. You initialize Git (one click in GitHub Desktop, or one command in the terminal). Then you make your first commit.

$ git init
# Sets up Git tracking in your parables-book folder

$ git add .
# Stages all files for saving

$ git commit -m "Started book project, outline and Chapter 1 rough draft"

This commit is your foundation. Everything else in your book's history builds from this point.

Week 2: Working with Claude

Chapter 2: The Good Samaritan

You write a rough draft of the Good Samaritan chapter in your voice. You commit it.

"Chapter 2 rough draft, Good Samaritan"
$ git add .
$ git commit -m "Chapter 2 rough draft, Good Samaritan"

Now you ask Claude to help strengthen the section on modern application. Claude gives you a revised version. You save it and commit.

"Chapter 2, Claude revision of modern application section"

You read Claude's revision. Most of it works, but one paragraph sounds like a self-help book rather than a sermon. You blend Claude's ideas with your pastoral voice.

"Chapter 2, blended Claude suggestions with my voice, restored pastoral register"

That third commit message names exactly what you did and why. Three months later, if something feels off about Chapter 2, this note tells you where to look.

Week 3: Branching to Experiment

Chapter 3 has two possible openings. You're not sure which is better.

Should Chapter 3 open with a personal story about sitting with a dying parishioner, or with the biblical context of the Prodigal Son's original Jewish audience? Both feel right. With Git, you don't have to choose now.

You create a branch called chapter3-personal-opening and write that version. Then you create chapter3-biblical-context and write that one. Two complete versions, neither touching your main manuscript.

$ git branch chapter3-personal-opening
# Creates the branch

$ git checkout chapter3-personal-opening
# Switches to it so you write there

You print both versions. You read them on a Saturday morning. You share them with your associate pastor. You both agree: the personal story is stronger. You switch back to main and merge that branch in.

$ git checkout main
# Switch back to your main manuscript

$ git merge chapter3-personal-opening
# Bring the chosen version in
Week 4: Going Back in Time

The opening you changed was better before you changed it.

You've been refining Chapter 2 for three weeks. Something is off. You go back through your commit history and find the version from Week 2, before Claude touched it. You read the opening paragraph. A directness, a specific detail about a conversation with a widow in your congregation, that got smoothed away in revision.

You restore just that opening paragraph from the earlier version. Git lets you pull one paragraph from the past while keeping everything else you've improved.

"Restored original Chapter 2 opening, the widow story is essential, don't smooth it"

That note is written to future-you. If you're ever tempted to revise that paragraph again, you'll see this message.

What this changes

You can experiment without fear. You can try Claude's suggestions without worry. You can branch into a risky direction and know your main manuscript is safe. None of this is possible when your file system is Chapter2_FINAL_v4b.docx.

Getting Started

Practical steps for non-programmers

Option A: GitHub Desktop (Recommended for Most Writers)

GitHub Desktop is a free application that gives you the full power of Git through a visual interface. No command line. You click buttons, write notes, and your manuscript history is maintained automatically.

  1. Download GitHub Desktop at desktop.github.com. Free for Mac and Windows.
  2. Create a free account at GitHub.com. This is where your manuscript history will be backed up online. Private repositories are free.
  3. In GitHub Desktop, choose Create New Repository. Name it after your book. Choose a folder on your computer. Click Create.
  4. Write your chapters as plain text or Markdown files in your book's folder.
  5. In GitHub Desktop, you'll see your changed files listed. Write a short note in the Summary field. Click Commit to main.
  6. Click Push to origin to send your committed version to GitHub online. This is your off-site backup.

That's the full workflow. Write. Commit with a note. Push online. Repeat.

Option B: Git in the Terminal

If you're comfortable with a terminal or command prompt, the three commands you'll use most are:

$ git add .
# Stages all your changes for saving

$ git commit -m "Chapter 3, added the parable of the talents application section"
# Saves a snapshot with your note

$ git push
# Sends it to GitHub as a backup

Option A (GitHub Desktop) does everything most writers need. There's no advantage to using the command line unless you prefer it.

What to write in

Git works best with plain text files. Use .md (Markdown) or .txt formats rather than Word documents. Markdown is a simple formatting system: type ## Chapter Title for a heading, **bold** for bold, and the rest is just writing. When you need a formatted version for an editor or publisher, you can export to Word or PDF.

The four tools below all save your chapters as plain Markdown files, which means Git can track every change line by line. Each one pairs with GitHub Desktop for Git management.

Typora Best for beginners
A word-processor-style Markdown editor. You see formatted text as you write, not Markdown syntax. Files save as plain .md files that Git tracks perfectly. One-time $15 purchase. Mac, Windows, Linux. Pair with GitHub Desktop for Git management.
VS Code Best Git integration
A free text editor from Microsoft with Git built in natively. You can commit and push directly from the sidebar without leaving the app. Add the extensions Markdown All in One (preview and shortcuts) and Code Spell Checker for a writing-ready setup. Mac, Windows, Linux.
iA Writer Best writing experience
A minimalist writing app with focus mode, strong typography, and clean Markdown support. Saves plain .md files. No built-in Git, so pair with GitHub Desktop. Mac and iOS ($49.99 Mac, subscription iOS). The cleanest writing environment of the four options.
Obsidian Best for note-heavy projects
A free writing and note-taking app built around Markdown files. The Longform plugin adds chapter management and word-count goals designed for book-length projects. Git integration is available via the Obsidian Git plugin. Takes more initial setup than the other options. Mac, Windows, Linux.

Start here: Typora and GitHub Desktop. The combination works in under an hour with no configuration. If you want Git controls built into your writing environment, use VS Code instead.

What to commit

Keep these files in your repository:

Chapter files. One file per chapter: chapter-01-introduction.md, chapter-02-good-samaritan.md, etc.

Structural documents. Your outline, chapter summaries, theological notes, overall arc.

Research and sources. Notes on commentaries, quotes you might use, reference material.

Prompts that worked. When you find a Claude prompt that produces useful results, save it in a text file. "Here is the prompt that got Claude to expand a sermon into a chapter without losing the preached voice." Future-you will thank you.

When to commit

  • At the end of every writing session, even if the chapter isn't finished
  • Before asking Claude for any significant revision
  • When you finish a complete draft of a chapter
  • When you finish incorporating feedback from your editor or co-author
  • Any time you think "I like this version and I want to be able to get back here"

How to write good commit messages

Your commit messages are the index to your manuscript's history. Write them for your future self, six months from now, trying to find the version with that one illustration.

✓ Chapter 3: expanded parable explanation based on Wesley's commentary on wealth
✓ Reworked Chapter 1 opening: now starts with the earthquake story from 2019 Honduras trip
✓ Claude revision: made theological terms more accessible for lay readers, checked against original
✓ Chapter 5 first complete draft, submitted to Pastor Williams for feedback
✗ Changes
✗ Stuff
✗ More editing

The specificity is what makes it useful. "Chapter 2 revision" tells you nothing in six months. "Chapter 2, restored the widow story after Claude removed it in polish pass" tells you exactly where to look.

Common Concerns

Questions writers ask before they start

"Isn't this overkill for a book?"
It depends on the project. For a short writing project with few revisions, it may be. For a book written over months with an AI collaborator, Git removes overhead you would otherwise manage manually through file names, email drafts, and your own memory. Commits replace the need for Chapter2_FINAL_v4b.docx.
"What if I mess it up?"
Git is designed to be reversible. Your files still exist on your computer. Your commits still exist in your history. Your GitHub backup still exists online. If something goes wrong and you're confused, paste the error message into Claude and ask for help. Claude can walk you through Git recovery steps.
"Do I have to use the command line?"
No. GitHub Desktop handles everything visually. Click to see your changes, type your commit message, click to commit, click to push. That's the full workflow. VS Code also has Git built into its sidebar if you want to stay inside one application.
"Can I still use Word or Google Docs?"
Yes, with caveats. Word documents and Google Docs use binary formats. Git can track them and save versions, but it cannot show you line-by-line differences between drafts the way it can with plain text. For the full benefit of Git, plain text formats like Markdown work best. Write your chapters in Markdown and export to Word when you need a formatted draft for an editor or publisher.
"What about my co-author or editor?"
When your book is on GitHub, you can invite a co-author, editor, or ministry team member as a collaborator. They can see the full history, suggest changes in their own branch, and you can review and merge their edits. No more "which version did you edit?" emails.
"Is my manuscript private on GitHub?"
Yes. When you create a repository on GitHub, you can make it private. Only you and anyone you explicitly invite can see it. Private repositories are free.
Privacy & .gitignore

Keeping private files private

Not everything belongs on GitHub. Your manuscript chapters and structural notes are good candidates for version control and online backup. But you may also have files you want to keep off the internet entirely: personal counseling notes that informed your writing, rough prayer journals, sensitive pastoral correspondence, or research you're not ready to share. Git has a built-in mechanism for this.

The .gitignore file

A .gitignore file is a plain text file that tells Git what to ignore. Any file or folder you list in it will not be tracked by Git and will not be uploaded to GitHub. It stays on your computer only. You create it once, put it in your repository folder, and Git respects it from that point forward.

Here is a simple example. Create a file named .gitignore (note the dot at the start) in your book's folder and add lines like these:

# Files and folders Git should ignore

personal-notes/
# A folder of private research or pastoral notes

private-drafts/
# Rough drafts you're not ready to share

sensitive-interviews.md
# A specific file you want kept off GitHub

*.private.md
# Any file ending in .private.md

Lines starting with # are comments for your own reference. Git ignores them. Everything else is a file name or folder name that Git will skip entirely.

How to create it

In GitHub Desktop: Open your book's folder in Finder or File Explorer. Create a new text file and name it exactly .gitignore (the dot is required; it must have no other extension). Open it in any text editor, add your list, and save. GitHub Desktop will recognize it automatically.

In the terminal: Navigate to your repository folder and run touch .gitignore, then open the file in any text editor to add your list.

What this means for your files

Files listed in .gitignore stay on your computer exactly as they are. Git simply ignores them — they are never tracked, never committed, and never sent to GitHub. Your normal computer backup system (Time Machine, iCloud, etc.) still backs them up as usual. You are only controlling what goes to GitHub, not what gets saved locally.

Once your .gitignore is in place, you don't need to think about it again. Add a file or folder to the list whenever you want something excluded, and Git will leave it alone.

Closing

What this gives you

Writing a book with Claude introduces a specific problem: you'll revise frequently, try experiments, and generate many versions of the same chapter over many months. Without a system, you manage that complexity through file names and memory, and things get lost.

Git solves that problem. Every version is saved. Every experiment can be tried on a branch without touching your main draft. Any revision that doesn't work can be undone. You can read commit messages from six months ago and see exactly what changed and when.

Git is free. GitHub Desktop takes an afternoon to learn. Start with Typora or VS Code, commit after every session, and push to GitHub for backup. Your manuscript history will take care of itself from there.
